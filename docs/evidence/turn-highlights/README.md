## Waveform: a separate backend/runtime defect, not a design choice

The original MP3 has `.bin` and metadata files but **no `.peaks.json` sidecar**. A real request to `/v1/desktop/sessions/8d652185377c/attachments/50d01a45566ce76e99e521ef0abcf9ca/waveform` on the isolated original copy returns **404**. `SupplementSoundLine` already calls `useWaveform` through this path; its fetch is not omitted. The flat state paints 8 canvas rows out of 88, rather than waiting indefinitely for peaks.

Further verification: the currently installed harness generation's Python cannot import `miniaudio`, while the repository development environment can. Backend `cache_media` writes peaks only when that optional decoder is available; the waveform route only reads existing sidecars. Thus runtime capability plus recovery of previously generated attachments need a companion backend/runtime fix. **This UI PR does not claim to fix that separate defect.**

For controlled UI waveform evidence only, the isolated copied store was supplied a sidecar using the existing production `compute_peaks` and `AttachmentStore.put_peaks` functions on the actual MP3. This is explicitly preparation, **not proof of automatic sidecar recovery**. The real route then returns **200**, with 240 peaks ranging from `0.0001` to `0.2062`; the rendered waveform paints 14/88 canvas rows. Its small shape reflects this particular recording's actual low amplitude, not a fabricated decorative waveform. [observations.json](observations.json) records the DOM and canvas facts.
