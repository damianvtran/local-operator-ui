mandatory rather than defaulted, because a keep-less call's only survivor is the NEWEST
generation in the root, which is not necessarily the selected one.

over the same file with one key duplicated.

## N6 - the readiness docstring and the failure classification

`managed-python.ts`, the `managedSelectionReady` paragraph, used to say Mach-O verification
"still runs against the seed, the staged copy and every candidate generation". It runs
against the seed and the staged copy; a reused generation is accepted on its identity alone,
which is sufficient because it is byte-identical to a staged copy that was verified. The
sentence now says that, and names the false claim it replaced.

The classification, with the same test both ways:

```
$ # the third cause bucket, before the fix
$ node scripts/run-desktop-tests.mjs scripts/python-bytecode-cache.test.mjs
✖ the setup failure dialog says what happened before what was recorded (0.747541ms)
ℹ pass 28
ℹ fail 1
  AssertionError [ERR_ASSERTION]: nothing was installed, so the copy must not say it was

$ # after the fix
$ node scripts/run-desktop-tests.mjs scripts/python-bytecode-cache.test.mjs
✔ the setup failure dialog says what happened before what was recorded (0.799125ms)
ℹ tests 29
ℹ pass 29
ℹ fail 0
```

`Backend preparation did not complete. <...>` is what `prepareManagedPython` throws when the
install callback returns false - a pip or network failure, where nothing was installed. The
`did not complete` alternation made it match the smoke bucket, so the user read "The backend
was installed but did not start correctly" about an install that never happened. The
alternation is gone from that bucket and the failure falls through to the generic cause,
which is true of it; the app's own sentence still follows under `The app recorded:`. No new
user-visible string was introduced - the correction chooses between sentences that already
existed - and the test pins both halves, so a real smoke failure still reads as one.
