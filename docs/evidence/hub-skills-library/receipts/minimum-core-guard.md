## Exact version authority and scope

The renderer reuses `useServerHealth()` / `serverHealthQueryKey=["server-health"]` in `shared/hooks/use-connectivity-status.ts`. Its desktop snapshot is `DaemonStatusSnapshot` (`src/shared/backend-status.ts`), with `version:string|null`, state, URL, instance ID and PID. MAIN's `backend.getStatus()` / `onStatusChange` are the authority, not the configured renderer origin or an installed generation. `src/main/index.ts` registers status against `backendService.getStatusSnapshot()` and desktop IPC against that **same** service's `requestDesktop()`. `backend-service.ts` sends desktop requests using its admitted `backendUrl`; `daemon-status.ts` derives snapshot URL/version from the admitted identity. `discovery.readIdentity()` reads the actual `/health` response's `result.version`. Settings already uses this MAIN status authority. No guessed capabilities package-version field was added.

The guard requires **attached + nonempty URL/instance ID + positive integer PID + strictly published X.Y.Z>=0.72.1**. Unknown/malformed/prerelease/dev versions fail closed, including0.72.1rc and0.72.2-dev. The existing main prefix comparator accepts suffixes, so it cannot by itself certify a published fixed release. Browser/Storybook direct health fallback is not promoted to desktop truth; without an explicit MAIN bridge, these writes are unavailable.

At invocation, `guardHubMutation()` subscribes **before** a fresh MAIN status read. A newer push wins a delayed positive pull. An identity URL/PID/instance change refuses an old intent even if the replacement version is positive. The real `desktopResult` closure executes inside that guard; listeners are removed in `finally`. Accepted in-flight work is neither replayed nor retrospectively aborted; every later invocation rechecks. This is a thin guard around the existing bridge/cache, not another daemon engine or a global connectivity rewrite. It is not an atomic server-side transaction with a future identity swap; core still owns authorization/CAS and the fixed backend behavior.

Actual guarded wire operations are six: `hub.policy`, `hub.check`, `hub.apply`, `hub.retry`, `hub.push`, `hub.applyAll`. They cover13 exercised hook arms: policy, per-link check, pull preview/confirm, pull/push retry, push preview/confirm, source-resolution via apply, legacy item apply/retry/check and apply-all. Browse inventories remain reads. Policy/link/detail/sidebar write controls are disabled with one keyed message: **“Hub changes require core {minimum} or newer. Browsing is still available.”** Unknown is not called outdated. Cancel/close/read detail remain available; disabled headings do not pretend to be busy spinners. Normal health polling temporarily blocks Hub writes, not browsing/global app interactions, and a previously verified positive version does not flash an upgrade notice during that poll.

Disabling new client commands does **not** repair autonomous behavior or existing policy state in an old daemon. The actual core fixes and release remain a separate requirement.
